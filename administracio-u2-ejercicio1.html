Objetivo y entorno

Objetivo: preparar un dominio de Active Directory sobre Windows Server 2025 y unir un cliente Windows 11 Pro. La comprobación incluye DNS, canal seguro, objeto del equipo y acceso con un usuario normal del dominio.

Bosque y dominio: asix.test. NetBIOS: ASIX. Usuario de prueba: ASIX\usuario01 — Usuario Prueba.

La red interna aísla el laboratorio y permite la comunicación entre las dos VM. Sin router ni otro adaptador, no ofrece salida a Internet. El DNS del cliente apunta al controlador del dominio, no a un DNS público ni al propio cliente.

Los procedimientos gráficos y de consola son alternativas. No se deben ejecutar de nuevo operaciones ya realizadas, como crear el bosque, unir el equipo o crear el usuario.

UNIDAD 2 · ACTIVIDAD 1

Preparar el servidor y la red interna

Mediante interfaz gráfica

  1. En el servidor, ejecutar sysdm.cpl, abrir Nombre de equipo → Cambiar y establecer SRV-DC01. Reiniciar para aplicar el nombre.
  2. Ejecutar ncpa.cpl. En Ethernet → Propiedades → TCP/IPv4, configurar IP 192.168.50.10, máscara 255.255.255.0, puerta de enlace vacía y DNS preferido 192.168.50.10.
  3. No desactivar IPv6. Comprobar hostname e ipconfig /all.
  4. Con las VM apagadas, en VirtualBox → Configuración → Red, conectar el adaptador 1 de ambas a Red interna, con el nombre exacto ASIX-U2 y cable conectado.

El servidor apunta a sí mismo como DNS porque alojará el servicio DNS de Active Directory. Antes de instalarlo es normal que esa dirección todavía no responda consultas DNS.

Alternativa por consola · servidor

La configuración parte del laboratorio indicado. No ejecutar estos comandos en el anfitrión. New-NetIPAddress añade una IP; no limpia automáticamente otras direcciones fijas.

# Windows PowerShell de 64 bits, como administrador, EN EL SERVIDOR.
# Si el nombre ya es SRV-DC01, no es necesario renombrarlo otra vez.
if ($env:COMPUTERNAME -ne 'SRV-DC01') {
    Rename-Computer -NewName 'SRV-DC01' -Restart
}

# Tras el reinicio, comprobar el nombre real del adaptador.
Get-NetAdapter

# En este laboratorio el adaptador se llama Ethernet.
# New-NetIPAddress se usa para añadir esta IP si todavía no existe.
# Si ya hay otra IP FIJA configurada, corregirla desde ncpa.cpl primero.
if (-not (Get-NetIPAddress -InterfaceAlias 'Ethernet' -AddressFamily IPv4 |
        Where-Object IPAddress -EQ '192.168.50.10')) {
    New-NetIPAddress -InterfaceAlias 'Ethernet' -IPAddress '192.168.50.10' -PrefixLength 24
}
Set-DnsClientServerAddress -InterfaceAlias 'Ethernet' -ServerAddresses '192.168.50.10'
hostname
ipconfig /all

UNIDAD 2 · ACTIVIDAD 1

Instalar Active Directory y DNS

Mediante interfaz gráfica

  1. Abrir Administrador del servidor → Administrar → Agregar roles y características.
  2. Elegir instalación basada en características o roles y seleccionar SRV-DC01.
  3. Seleccionar Servicios de dominio de Active Directory y Servidor DNS, aceptando sus herramientas de administración.
  4. Completar la instalación. Instalar los roles no crea todavía el dominio.

Resultado obtenido por consola: Success: True, Restart Needed: No y Exit Code: Success.

Alternativa por consola · servidor

En la práctica se realizó esta instalación por PowerShell. IncludeManagementTools añade las consolas y módulos de administración.

# EN SRV-DC01, Windows PowerShell de 64 bits como administrador.
[Environment]::Is64BitProcess
Import-Module ServerManager
Install-WindowsFeature -Name AD-Domain-Services,DNS -IncludeManagementTools
Get-WindowsFeature -Name AD-Domain-Services,DNS
Incidencia resuelta · PowerShell de 32 bits

Install-WindowsFeature no se reconocía y ServerManager no se encontraba. La consola era de 32 bits: Is64BitProcess devolvía False. El acceso a System32 estaba sujeto a redirección y no mostraba el módulo correcto.

Desde esa consola de 32 bits se abrió Windows PowerShell de 64 bits con:

& "$env:windir\Sysnative\WindowsPowerShell\v1.0\powershell.exe"

Después Is64BitProcess y Test-Path devolvieron True. La instalación de roles terminó correctamente. Sysnative se utiliza en este caso desde un proceso de 32 bits; desde uno de 64 bits se usa la ruta normal System32.

[Environment]::Is64BitProcess
Test-Path "$env:windir\System32\WindowsPowerShell\v1.0\Modules\ServerManager"

UNIDAD 2 · ACTIVIDAD 1

Crear el bosque asix.test

Promoción mediante el asistente

  1. En la bandera de notificaciones del Administrador del servidor, pulsar Promover este servidor a controlador de dominio.
  2. Seleccionar Agregar un nuevo bosque y dominio raíz asix.test.
  3. En Opciones del controlador de dominio, conservar DNS y catálogo global. Establecer personalmente la contraseña DSRM y conservarla fuera de las capturas.
  4. En Opciones de DNS, dejar Crear delegación DNS sin marcar. El aviso es esperado al no existir una zona superior en este laboratorio aislado.
  5. En Opciones adicionales, comprobar el nombre NetBIOS ASIX.
  6. Conservar las rutas predeterminadas y revisar las opciones. Esperar a que las comprobaciones de requisitos previos finalicen correctamente.
  7. Pulsar Instalar. El servidor se reinicia al terminar la promoción.
  8. Iniciar sesión como ASIX\Administrador, con la contraseña del administrador del servidor. La contraseña DSRM se utiliza para recuperación, no para este inicio normal.
Alternativa por consola · servidor

Este bloque sustituye al asistente completo. Solicita la contraseña DSRM de forma oculta y conserva las comprobaciones y la confirmación. No ejecutarlo si asix.test ya existe.

# ALTERNATIVA al asistente: solo si el bosque NO está creado todavía.
# Ejecutar en SRV-DC01 con permisos de administrador.
Import-Module ADDSDeployment
$dsrm = Read-Host 'Contraseña de recuperación DSRM' -AsSecureString
$forest = @{
    DomainName = 'asix.test'
    DomainNetbiosName = 'ASIX'
    InstallDns = $true
    CreateDnsDelegation = $false
    SafeModeAdministratorPassword = $dsrm
}
Install-ADDSForest @forest
# Revisar y confirmar cuando lo solicite. El servidor se reinicia.

UNIDAD 2 · ACTIVIDAD 1

Comprobar el dominio creado

En el servidor promovido, abrir Windows PowerShell de 64 bits y comprobar:

Get-ADDomain | Select-Object DNSRoot,NetBIOSName

Resultado comprobado: DNSRoot asix.test y NetBIOSName ASIX. El dominio está creado; el servidor debe permanecer encendido durante las operaciones del cliente.

UNIDAD 2 · ACTIVIDAD 1

Preparar Windows 11 Pro

Nombre y direccionamiento del cliente

  1. Iniciar sesión con un administrador local en windows11 pro clonar.
  2. En sysdm.cpl, cambiar el nombre a CLI-W11-01, conservando inicialmente el grupo de trabajo. Reiniciar.
  3. En ncpa.cpl → Ethernet → TCP/IPv4, configurar 192.168.50.20, máscara 255.255.255.0, puerta de enlace vacía y DNS 192.168.50.10.
  4. Comprobar nombre y red con hostname e ipconfig /all.

Corrección realizada: el cliente tenía inicialmente 192.168.50.20 como DNS. Se corrigió a 192.168.50.10, el servidor DNS del dominio. La IP propia del cliente sigue siendo .20.

El cliente conservaba restricciones locales de la unidad 1. Estas se revisan desde una cuenta administradora local antes de continuar. El restablecimiento de políticas del cliente no se ejecuta en el servidor ni en un equipo ya unido al dominio. No es necesario desactivar el firewall para esta práctica.

Alternativa por consola · cliente, administrador local

El cambio de nombre reinicia el cliente. Tras iniciar sesión, continuar con la red. El nombre del adaptador debe comprobarse con Get-NetAdapter.

# EN EL CLIENTE, Windows PowerShell como administrador local.
if ($env:COMPUTERNAME -ne 'CLI-W11-01') {
    Rename-Computer -NewName 'CLI-W11-01' -Restart
}

# Tras el reinicio, comprobar que el adaptador se llama Ethernet.
Get-NetAdapter
# Si existe otra IP FIJA, corregirla antes desde ncpa.cpl.
if (-not (Get-NetIPAddress -InterfaceAlias 'Ethernet' -AddressFamily IPv4 |
        Where-Object IPAddress -EQ '192.168.50.20')) {
    New-NetIPAddress -InterfaceAlias 'Ethernet' -IPAddress '192.168.50.20' -PrefixLength 24
}
Set-DnsClientServerAddress -InterfaceAlias 'Ethernet' -ServerAddresses '192.168.50.10'
hostname
ipconfig /all

UNIDAD 2 · ACTIVIDAD 1

Localizar el controlador de dominio

En el cliente, con el servidor encendido:

nslookup asix.test
nltest /dsgetdc:asix.test

Resultado obtenido: asix.test se resuelve a 192.168.50.10. nltest identifica \\SRV-DC01.asix.test, dirección \\192.168.50.10, dominio y bosque asix.test, y termina correctamente.

nslookup mostró primero un timeout y el nombre del servidor como UnKnown, pero después obtuvo la dirección solicitada. La consulta inversa del servidor DNS podría explicar ese aviso, aunque no se diagnosticó de forma concluyente. No se presenta como un fallo resuelto: la localización del controlador y las pruebas posteriores confirmaron el funcionamiento necesario para unir el cliente.

UNIDAD 2 · ACTIVIDAD 1

Unir el cliente al dominio

Unión mediante interfaz gráfica

  1. En CLI-W11-01 ejecutar sysdm.cpl.
  2. En Nombre de equipo, pulsar Cambiar. No basta con editar el campo Descripción del equipo.
  3. Seleccionar Dominio, introducir asix.test y aceptar.
  4. Cuando se pidan credenciales, utilizar ASIX\Administrador y su contraseña. En un entorno real pueden utilizarse permisos delegados para la unión.
  5. Guardar el mensaje de bienvenida al dominio y reiniciar el cliente.
Alternativa por consola · cliente, administrador local

Get-Credential solicita la contraseña sin escribirla en el código. Este bloque sustituye a la unión gráfica y reinicia el cliente.

# ALTERNATIVA a sysdm.cpl: ejecutar en CLI-W11-01 como administrador local.
# Solo si todavía no pertenece al dominio.
$credential = Get-Credential -UserName 'ASIX\Administrador' -Message 'Credenciales autorizadas para unir el cliente'
Add-Computer -DomainName 'asix.test' -Credential $credential -PassThru -Verbose -Restart

UNIDAD 2 · ACTIVIDAD 1

Verificar la pertenencia y el canal seguro

Tras el reinicio, abrir PowerShell como administrador en el cliente y ejecutar:

Get-CimInstance Win32_ComputerSystem | Select-Object Name,Domain,PartOfDomain
Test-ComputerSecureChannel -Verbose

Resultado comprobado: nombre CLI-W11-01, dominio asix.test, PartOfDomain: True y canal seguro True. El mensaje confirma que el canal entre el equipo y el dominio está en buen estado.

En SRV-DC01, ejecutar dsa.msc, expandir asix.test → Computers y localizar CLI-W11-01.

Alternativa por consola · servidor

Consulta equivalente al objeto mostrado en Computers. Se ejecuta en el servidor con el módulo ActiveDirectory.

Get-ADComputer -Identity 'CLI-W11-01' -Properties DNSHostName | Select-Object Name,DNSHostName,Enabled

UNIDAD 2 · ACTIVIDAD 1

Crear Usuario Prueba

Crear una cuenta de prueba sin privilegios administrativos

  1. En SRV-DC01, abrir dsa.msc y seleccionar asix.test → Users.
  2. Elegir Nuevo → Usuario.
  3. Nombre de pila Usuario, apellidos Prueba y nombre completo Usuario Prueba.
  4. Inicio de sesión usuario01@asix.test y nombre corto ASIX\usuario01.
  5. Definir una contraseña que cumpla la política del dominio y marcar El usuario debe cambiar la contraseña en el siguiente inicio de sesión.
  6. Finalizar. No añadir la cuenta a Administradores del dominio ni a Administradores locales.
Alternativa por consola · servidor

Solo si usuario01 aún no existe. La contraseña se solicita como SecureString y no aparece en el HTML. No se reutilizan nombres personales para esta cuenta.

# ALTERNATIVA al asistente de usuarios: ejecutar EN SRV-DC01.
Import-Module ActiveDirectory
$password = Read-Host 'Contraseña inicial de usuario01' -AsSecureString
$user = @{
    Name = 'Usuario Prueba'
    GivenName = 'Usuario'
    Surname = 'Prueba'
    DisplayName = 'Usuario Prueba'
    SamAccountName = 'usuario01'
    UserPrincipalName = 'usuario01@asix.test'
    Path = 'CN=Users,DC=asix,DC=test'
    AccountPassword = $password
    Enabled = $true
    ChangePasswordAtLogon = $true
}
New-ADUser @user
Get-ADUser -Identity 'usuario01' -Properties UserPrincipalName |
    Select-Object Name,SamAccountName,UserPrincipalName,Enabled

UNIDAD 2 · ACTIVIDAD 1

Iniciar sesión con usuario01

  1. En CLI-W11-01 cerrar la sesión actual y seleccionar Otro usuario.
  2. Introducir ASIX\usuario01 y la contraseña inicial configurada en el servidor.
  3. Cuando se solicite el cambio: la contraseña anterior es la inicial; elegir una nueva que cumpla la política y repetirla en Confirmar. Desde ese momento se utiliza la nueva.
  4. Esperar a la preparación del escritorio.
  5. Abrir PowerShell normal, sin elevarlo con otra cuenta, y ejecutar:
whoami
hostname

Identidad de la sesión: asix\usuario01 en el equipo CLI-W11-01. La pertenencia al dominio, el canal seguro y el objeto del equipo se verificaron por separado; esta última prueba documenta el acceso con una cuenta normal del dominio.

Si el cambio de contraseña falla, revisar el teclado, Bloq Mayús y los requisitos de la política. No incluir contraseñas ni respuestas de recuperación en capturas o código.

RESULTADO

Conclusión de la actividad

Se ha creado el dominio asix.test en SRV-DC01, con Active Directory y DNS. El cliente CLI-W11-01 se ha unido al dominio y devuelve True tanto en PartOfDomain como en la prueba del canal seguro. Su objeto está presente en Active Directory y se ha preparado la cuenta genérica Usuario Prueba / usuario01 para comprobar el inicio de sesión.

La configuración DNS del cliente es esencial: debe consultar a 192.168.50.10. La práctica también documenta la resolución de la consola PowerShell de 32 bits, la corrección del DNS del cliente y la diferencia entre el aviso de delegación DNS y un error que bloquee la promoción.
