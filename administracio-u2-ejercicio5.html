Administración del dominio

01

Máquinas y requisitos

No se necesita una ISO nueva. Utilizamos las dos máquinas ya instaladas: SRV-DC01 con Windows Server 2025 y CLI-W11-01 con Windows 11 Pro, unido al dominio asix.test. RSAT se incorpora como característica opcional de Windows.

EquipoDirección de laboratorioFunción
SRV-DC01192.168.50.10Controlador de dominio y DNS
CLI-W11-01192.168.50.20 · DNS 192.168.50.10Cliente desde el que se abren las consolas

Ambas VM deben estar encendidas y conectadas a la misma red interna ASIX-U2. El enunciado menciona Enterprise; este laboratorio utiliza Pro, edición compatible con RSAT.

La red interna aislada no proporciona Internet. Para descargar RSAT necesitaremos una salida temporal a Internet o un origen de características opcionales compatible con la versión exacta de Windows. Una ISO normal de Windows no equivale a la de Languages and Optional Features. Antes de cambiar adaptadores revisaremos la configuración actual; conservaremos el DNS del dominio para las pruebas.

La instalación necesita elevación local. Para administrar el dominio utilizaremos una cuenta autorizada; ser administrador local no otorga permisos en Active Directory. En este laboratorio puede usarse la cuenta administrativa del dominio para la sesión de administración, sin convertir a los usuarios habituales de MaderasNexo en administradores.

02

¿Qué incluye RSAT?

RSAT agrupa paquetes de consolas y comandos para administrar servicios de Windows Server desde un cliente. La lista depende de la versión y arquitectura de Windows: no equivale a un número fijo de consolas. Instalaremos las tres necesarias para el enunciado.

Dominio y usuarios · herramientas de esta práctica

Active Directory: usuarios, grupos, equipos y unidades organizativas. Abriremos dsa.msc y consultaremos MaderasNexo.

Directivas de grupo: consultar y administrar GPO y sus vínculos. Abriremos gpmc.msc; aquí no crearemos ni modificaremos directivas.

Servidores y almacenamiento

Administrador del servidor — esta práctica: añadir SRV-DC01 y consultar su estado mediante ServerManager.exe.

Servicios de archivos: herramientas para funciones como cuotas, clasificación y otros servicios de almacenamiento, según el componente instalado.

Servicios de red

DNS: gestionar zonas y registros de nombres. DHCP: gestionar ámbitos, concesiones y reservas de direcciones IP.

Virtualización y alta disponibilidad

Hyper-V: administrar hosts y máquinas virtuales; sus herramientas se habilitan mediante las características de Windows correspondientes. Clústeres: administrar alta disponibilidad entre servidores. No son necesarios para esta actividad.

Certificados y actualizaciones

Servicios de certificados: administrar autoridades de certificación y certificados. WSUS: gestionar actualizaciones centralizadas. La forma de obtener estas consolas depende del componente y de Windows; no todas se instalan con el mismo comando de capacidades RSAT.

03

Procedimiento de la práctica

1. Comprobar identidad, DNS y dominio

En Windows PowerShell de 64 bits del cliente, consultar:

hostname
whoami
Get-CimInstance Win32_ComputerSystem | Select-Object Name,Domain,PartOfDomain
Get-DnsClientServerAddress -AddressFamily IPv4
nltest /dsgetdc:asix.test
Test-ComputerSecureChannel -Verbose

Esperamos CLI-W11-01, dominio asix.test, PartOfDomain=True, DNS del laboratorio y canal seguro correcto. Resolver incidencias antes de continuar.

2. Instalar las tres herramientas

Desde Inicio, buscar Características opcionales, abrir Ver características y buscar RSAT. Seleccionar herramientas de AD DS/AD LDS, Administración de directivas de grupo y Administrador del servidor. Instalar y reiniciar si lo solicita.

Alternativa por consola · Windows PowerShell como administrador
$herramientas = @(
    'Rsat.ActiveDirectory.DS-LDS.Tools~~~~0.0.1.0'
    'Rsat.GroupPolicy.Management.Tools~~~~0.0.1.0'
    'Rsat.ServerManager.Tools~~~~0.0.1.0'
)
foreach ($herramienta in $herramientas) {
    Add-WindowsCapability -Online -Name $herramienta -ErrorAction Stop
}
Get-WindowsCapability -Online |
    Where-Object { $_.Name -in $herramientas } |
    Select-Object Name,State

Las tres deben aparecer como Installed. Si falla la descarga, anotar el código y revisar conectividad y origen de instalación antes de repetir. No instalar todos los paquetes por defecto.

3. Consultar Active Directory

Ejecutar dsa.msc desde el cliente con una cuenta autorizada del dominio. Abrir asix.test → MaderasNexo. Expandir departamentos y sus OU Usuarios y Equipos, además de Grupos → Globales y DominioLocal.

Consultar Administración → Usuarios, las propiedades de adm01 y los miembros de GG_MN_ADM y DL_MN_ADM_M. Debe verse el usuario en el grupo global y el global dentro del grupo de dominio local. Compararemos con el trabajo del ejercicio 3; esta consulta no vuelve a crear la estructura.

4. Consultar el servidor

Ejecutar ServerManager.exe → Administrar → Agregar servidores → buscar SRV-DC01 en Active Directory y añadirlo. Entrar en Todos los servidores y esperar a que recopile información.

Que el servidor figure en la lista no demuestra por sí solo que su administración remota funcione: comprobar la columna de capacidad de administración. Si falla, revisar DNS, credenciales y que en SRV-DC01 esté habilitada Administración remota en Servidor local. No desactivar el cortafuegos completo.

Consulta complementaria de conectividad
Resolve-DnsName SRV-DC01.asix.test
Test-WSMan SRV-DC01.asix.test

Un resultado correcto de Test-WSMan comprueba la respuesta de WinRM, pero no garantiza permisos para todas las operaciones. Usaremos el nombre del servidor y la autenticación del dominio.

5. Consultar las directivas del dominio

Ejecutar gpmc.msc → Bosque asix.test → Dominios → asix.test. Mostrar las OU y Objetos de directiva de grupo. Consultar los vínculos existentes sin editarlos; las GPO específicas del perfil móvil se configurarán en el ejercicio 6.

Objetivo de verificación: abrir las tres consolas desde CLI-W11-01, consultar la estructura real de MaderasNexo, obtener información de SRV-DC01 y visualizar las GPO del dominio. La evidencia muestra el servidor en línea con el aviso «contadores de rendimiento no iniciados»; este aviso no impide consultar su información.

+

Preparación e incidencias resueltas

Canal de confianza del cliente

CLI-W11-01 figuraba unido al dominio y encontraba SRV-DC01, pero Test-ComputerSecureChannel devolvía False. Desde Windows PowerShell elevado del cliente se reparó la relación con credenciales administrativas del dominio. La comprobación posterior devolvió True.

$credencial = Get-Credential -UserName 'ASIX\Administrador' -Message 'Credenciales del administrador del dominio'
Test-ComputerSecureChannel -Repair -Server 'SRV-DC01.asix.test' -Credential $credencial -Verbose
Test-ComputerSecureChannel -Server 'SRV-DC01.asix.test' -Verbose
Descarga de RSAT y permisos de instalación

La consulta inicial de capacidades requería elevación. Se abrió Windows PowerShell como administrador. Para descargar los componentes se añadió al cliente un segundo adaptador NAT, manteniendo el adaptador 1 en ASIX-U2. Test-NetConnection www.microsoft.com -Port 443 devolvió TcpTestSucceeded=True por Ethernet 2; el canal del dominio siguió devolviendo True.

La primera instalación tardó considerablemente. Se consultaron DISM y CBS; CBS mostraba actividad reciente y procesamiento de paquetes de Server Manager. Se esperó a que terminara, sin ejecutar instalaciones simultáneas. La primera finalizó con RestartNeeded=False. La captura 2 documenta el estado final de los tres paquetes.

Credenciales de las consolas y estado del servidor

La apertura inicial de Active Directory produjo un error de usuario o contraseña. La consola se abrió correctamente mediante runas con ASIX\Administrador. Las tres consolas pueden iniciarse así desde el cliente; la contraseña se introduce de forma interactiva, sin guardarla en el HTML.

runas /user:ASIX\Administrador "mmc.exe dsa.msc"
runas /user:ASIX\Administrador "ServerManager.exe"
runas /user:ASIX\Administrador "mmc.exe gpmc.msc"

En Todos los servidores, SRV-DC01 apareció en línea. Los eventos registrados y los contadores de rendimiento pendientes se distinguen de un fallo de conexión; esta actividad no pretende corregir todos los eventos históricos del servidor.
